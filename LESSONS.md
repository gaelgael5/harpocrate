# Leçons

- [build] Quand on ajoute une dep Python à `backend/pyproject.toml`, l'ajouter AUSSI dans la liste hardcodée du `backend/Dockerfile` (lignes 33-50). Le commentaire ligne 52 prévient. Sinon `ModuleNotFoundError` au boot du container après `pull latest`. Refactor à venir : faire lire pyproject.toml directement.
- [replication] add_node lève désormais NodeAlreadyExistsError (sous-classe d'InvalidPairingPreconditionError) sur conflit UNIQUE(label/application_name) ; les endpoints pairing v2 mappent en 409 avec `existing_node`. Le param `force` (request body) déclenche un DELETE+DROP ROLE+INSERT atomique pour remplacer le node existant. Audit log : `pairing.master_node_replaced`. Voir le plan `docs/superpowers/plans/2026-05-13-pairing-replace-existing-node.md`. Validation e2e manuelle différée — nécessite le master sur LXC 192.168.10.196 + standby sur 192.168.10.198 avec les nouvelles images.
- [pairing-exec] Le wizard pairing exécute désormais les 7 étapes côté serveur via aiodocker (mode docker_compose_auto, détecté via /.dockerenv + socket monté) ou via asyncssh (mode native, creds saisies une fois). Stepper de progression côté frontend, retry depuis l'étape N, audit log pairing.exec_step_*. SSHTerminal + SSHCredentialsModal supprimés. Plan : docs/superpowers/plans/2026-05-14-pairing-server-execution.md.
- [api] FastAPI `response_model=X` filtre **silencieusement** toute clé non déclarée dans le modèle Pydantic. Symptôme observé : la valeur est dans le dict construit côté backend, mais l'HTTP renvoie un payload tronqué côté client. Tout nouveau champ ajouté à un payload de réponse doit être déclaré dans le DTO ET couvert par un test qui asserte sa présence dans `r.json()`. Régression bloquée par `test_confirm_v2_does_not_require_auth` après l'incident `master_postgres_password absent du payload pairing`.
- [pairing-exec] `aiodocker container.start()` retourne dès que Docker a lancé le process Postgres, PAS quand Postgres accepte les connexions. Toute action qui suit (psql, socket Unix) doit attendre `pg_isready` en boucle avec timeout, sinon faux échec sur "socket No such file or directory". Implémenté dans `DockerExecutor._step_start_pg` (loop pg_isready 30s) et dans le shell de `NativeSshExecutor` côté `start_pg_container`.
- [pairing-exec] Le pool asyncpg du backend lit `settings.effective_db_dsn` **une seule fois** à `init_pool()`. Quand le wizard pairing écrit le password override en cours de route (step 6), il faut `db_pool.refresh_pool()` après le démarrage de Postgres (hook `on_pg_started` câblé dans le router WS sur step_done de `start_pg_container`) — sinon le backend reste en 503 `password authentication failed` jusqu'à un restart manuel.
- [db] **Toujours utiliser `settings.effective_db_dsn`** (pas `settings.db_dsn`) pour toute connexion DB runtime (asyncpg.connect, pg_dump, psql, etc.). `db_dsn` lit le `.env` brut ; `effective_db_dsn` applique le password override écrit par le wizard pairing standby. Sinon les composants non-pool (LISTEN dans `cluster_sync._listen_loop`, `backup_service`, `snapshot_scheduler`) continuent à se connecter avec l'ancien password après pairing et bouclent sur `password authentication failed`. Régression repérée après un pairing standby où `cluster_listen_error` continuait à boucler malgré le `refresh_pool`.
- [db] **Ne JAMAIS capturer le pool asyncpg dans une classe ou closure long-running.** Toujours appeler `await db_pool.get_pool()` au moment de chaque acquisition. Sinon, après `refresh_pool()` (déclenché par le wizard pairing standby), la référence pointe vers un pool fermé → boucle infinie sur `pool is closed`. Touche : `ClusterSync`, `ScheduledBackupsScheduler`, `SnapshotScheduler`, `SyncConsumer`, `SyncPublisher`, et les closures du lifespan FastAPI (`_wallet_purge_loop`, `_replication_refresh_loop`, etc.). Le pattern correct : `pool = await get_pool(); async with pool.acquire() as conn: ...` par tick.
- [pairing-exec] Sur un Postgres en mode standby (recovery), `LISTEN` est refusé par le serveur (`cannot execute LISTEN during recovery` — sémantique PG, pas un bug réseau). `ClusterSync._listen_loop` détecte ça via `SELECT pg_is_in_recovery()` au début de chaque tentative de connexion et entre en sleep long (60s) en attendant une éventuelle promotion. Aucun log d'erreur tant qu'on est en standby — état nominal pour ce mode (`cluster_listen_skipped_standby_mode` info une seule fois).
- [http] **Toujours catcher les exceptions de DB inaccessible au niveau middleware HTTP**, pas dans chaque endpoint. Le middleware `db_availability` (le plus externe) transforme `socket.gaierror`, `ConnectionRefusedError`, `asyncpg.InterfaceError`, `asyncpg.InvalidPasswordError`, `asyncpg.PostgresConnectionError` en 503 `db_unavailable` propre avec `Retry-After: 5`, log structlog warning court (pas error, pas traceback). Sans ce middleware, pendant le wizard pairing standby (Postgres stoppé entre step 1 et step 7), les requêtes admin remontent en 500 avec traceback ASGI complet dans les logs. Starlette/anyio enveloppent les exceptions dans `BaseExceptionGroup` imbriqués — le middleware unwrap récursivement pour matcher.
- [replication] Failover MVP = promotion manuelle guidée via UI : `pg_promote(wait=true)` + nettoyage `replication.is_standby_of=NULL` dans system_metadata + audit log `replication.promoted_to_master`. L'admin garde la **responsabilité de stopper l'ancien master AVANT** la promotion (modale exige double check-box : `confirm_master_down` + `confirm_clients_will_be_reconfigured`). Pas de détection split-brain auto, pas de rebuild auto de l'ancien master en standby. Endpoints : `GET /v1/admin/replication/can-promote` (auto-hide UI) + `POST /v1/admin/replication/promote`. Doc opérationnelle : `docs/operations/replication-failover.md`. Plan TDD : `docs/superpowers/plans/2026-05-14-failover-mvp.md`.
